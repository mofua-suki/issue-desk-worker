# 受入条件の実行分担と検証診断

受付が `view.executionPlan`（版1）と `executionPlanSHA` を配った依頼では、証拠型を `fixed_test`・`report_comment`・`external_check` に分ける。計画のない依頼は従来の経路を使う。Workerのcapabilitiesは `executionPlanVersion: 1` を返す。

外部確認だけの仕事は実装AIを起動せずコントローラー待ちにする。報告訂正だけの仕事は読み取り専用で根拠を照合し、訂正文を投稿する。製品テストや差分PRを作らない。元の依頼全体は背景として保持し、今回の担当条件を別に示す。削除・権限・対象SHAの承認と既存の回数・使用量上限は維持する。

`controllerTest` はコントローラーが固定検証から作った記録、`controllerReport` は投稿済みの訂正報告を照合する目印と本文指紋。実装モデルの自由な結果をこれらの欄へコピーしない。投稿成功は報告の投稿を証明し、配置・実機確認の成功を証明しない。

訂正報告の送信直前の担当確認で担当を失った場合、生成済みの報告を保持し、次の取得で担当とepochを確認してから送信する。送信結果が不明な場合は投稿の目印を照合し、目印が見つからなくても再投稿しない。

固定検証の `diagnostic` は実行SHA・基点、解決済みコマンド、計測した環境、開始・終了、期限、終了理由、プロセス終了状態とCPU時間、段階の出力、秘匿したアサーション周辺を保存する。生ログ全体やプロセス環境は保存しない。この診断はjournalから修復AI入力と受付の `fixedTestDiagnostic` へ渡す。欠測を合格にせず、原因不明を変更由来と確定しない。

実装中の固定テストが不合格（実行不能・証拠の欠測を除く）のときは、修復AIを呼ぶ前に同じ作業ツリー・同じコマンドで1回だけ再実行する。再実行で合格すれば修復せず合格として進め、`detail` の先頭に「不安定な失敗（再実行で合格）」と1回目の要点（時間切れ・失敗したテスト名など）を残し、修復の回数（`FixedTestFailures`）は増やさない。再実行も不合格なら、2回目の結果で修復し、再実行は修復の回数に数えない。最終承認後の固定テストは再実行せず保留する。

## 固定テストと再開

`view.workerExecution`には同じgeneration・epochで観測した段階別時間、欠落、AI修正時間、固定テスト回数と各回の結果、工程記録を載せる。未観測の時間は省略し、観測した0と区別する。各回の結果は先頭100件、工程記録は直近100件まで送る。

固定テストと全テストの切詰め前の出力からテスト識別・診断指紋・実行条件を作り、journalと最終結果へ保存・報告する。完全な合格証拠には対象SHA・基点SHA・実行条件・実行完了記録が必要で、証拠と観測の対象・条件が一致しなければ採用しない。出力切詰め、打切り、未対応形式、測定条件の欠測、未コミットの木は原因確定の根拠にしない。

検証済みの前回レビューが同一世代・同一依頼・同一差分で保留済みなら、固定テストと証拠の確認後、指摘と保留理由を保持して保留する。別PCからの持ち越しも差分・世代・依頼と実装報告を照合し、比較できない場合は通常の実装とレビューを行う。重大指摘は修正へ戻し、不正または不足した比較資料で反復指摘を確定しない。最終承認済みheadの公開続行では重大指摘を降格せず保留する。

別headでも同じ重大指摘が残る場合の反復保留、保存済み保持項目の持ち越しと配送の契約は[Issue・PRへの投稿](issue-comments.md#承認時の後続案)に定める。

状態の `diffFingerprint` は、一意なmerge-baseからheadまでの変更を、パスの生バイト順に並べてSHA-256で計算し、`sha256:`と16進数で表す。各項目はパス長（8バイトのビッグエンディアン）、パス、変更前後の各6桁のモード、変更前後それぞれの内容長（同じ8バイト形式）と内容をこの順で連結する。存在しない側はモード `000000` と空内容、サブモジュールはオブジェクトIDを内容とする。リネームは削除と追加として扱う。既定ブランチを衝突解決や手編集なしで取り込んだだけのhead上のマージは、取り込み前のheadまで遡って計算する。merge-baseが一意でない場合や内容を読めない場合など、計算できなければ欄を省略する。

マージ前のPR照合で不一致があれば `review_held` とし、`view.mergePullCheck` に `phase`（`initial` または `final`）、不一致の `checks`（`field` と `kind`）、`waiting` を記録する。番号、open状態、draft・merged、head/baseのrefとリポジトリ、head SHAを照合する。`mergeable` のみ未確認なら上限付きで待ち、所有権などのゲートを再確認して再取得する。待機上限に達すると `kind: unconfirmed`、`waiting: true` で保留し、その他の不一致は `kind: mismatch`、`waiting: false` で保留する。

## 実装報告と使用量

初回実装のcompleted報告と、未完了続行・固定テスト修復で正常に受信した報告は、使用量を送信する前にjournalへ保存する。使用量の送信に失敗した場合も報告と未送信の使用量を保持し、再開時に使用量を送信してから保存済み報告を処理する。呼び出し失敗や停止時の回答は先に保存しない。

completedの実装報告が内容検査に失敗した場合、同じ実行先・会話で報告だけを最大1回補完する。補完は実装回数に含み、開始前に記録し、承認済み回数上限とServerの使用量判断を適用する。通信・認証失敗、question・failed、停止は報告不備として再送しない。補完は読取専用で行い、会話IDがない場合、実行先が無効な場合、または編集禁止を保証できない場合は保留する。試行済み状態を保存し、中断後も同じ報告を再補完しない。

レビュー差し戻し後の再実装も開始前に回数を数え、毎回Serverの使用量判断を受ける。補完回数と再実装回数は総実装回数に含み、それぞれ `reportCompletionRuns` と `reviewReworkRuns` に累積する。利用者起点か自動実行かの判定では総回数から補完回数を引く。

中断や時間切れ時のCodex使用量は、会話記録にある完了した応答の累計から回収する。処理中だった応答の消費分は復元できず、不完全な記録などで回収できない値は欠測とし、0にしない。固定テスト不合格後の修正の使用量stepは実装（競合解消中は競合解消）、報告補完は実装報告補完とする。

範囲縮小の申請結果は各Workerの状態に `scopeNarrowed` と `scopeNarrowFailed` として累積する。Worker間では自動集約されず、状態の削除時には失われる。申請前には受付がブランチHEADを参照できるよう変更をPushする。
