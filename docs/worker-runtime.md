# 仕事の取得・公開・再開

## 仕事取得とlease

ホスト全体の同時実行枠とリポジトリ別の上限はServer配信の担当表に従います。各仕事のleaseを独立して更新します。依頼キューは全体のpollとは独立して、処理完了から15秒後に同じschedulerで直列に確認します。環境の再検査・作業ツリーの掃除・仕事取得は全体のpollで行い、取得失敗の待機中は依頼確認も待機します。実行設定の版が変わった場合は新規取得を止め、依頼の受け取りも止め、進行中の仕事を完了してから再起動します。

lease延長の接続失敗・5xx・要求単位の時間切れは、最後に確認した期限内で1秒から最大10秒の待機を挟んで再試行します。公開前の所有確認も延長成功とlease・epochの応答照合を待ちます。公開と最終報告には有効なleaseとepochが必要です。lease喪失・不正応答・期限到達では実行と公開を止めます。

空き枠の仕事取得が一時的に失敗した場合、所有中の仕事を継続し、1秒から最大10秒まで延びる待機の後に新しい取得を試みます。成功時に待機間隔を戻します。応答を失った取得要求は再送しません。回復までheartbeatのreadyをfalseとし、busy・実行件数・起動検査のchecksは実態を報告し続けます。

非一時的な取得エラー（認証・権限拒否、契約不一致など）、不正な配布応答、実行中の仕事の重複配布、リポジトリ枠の不一致とその返却失敗では、新規取得を止め、WaitGroupで実行と結果報告の完了を最大5分待ちます。この間もlease更新と公開前の所有確認を続けます。5分で残った仕事を取り消し、この期限到達による取消し後の終了処理は最大5秒で打ち切ります。SIGTERMや設定変更などの通常停止では、終了処理をWaitGroupで待ちます。仕事単位の実行・報告エラーは他の仕事を止めません。実行エラーを一般的な失敗として確定報告せず、保存済みの工程・結果・未送信使用量を保持し、lease期限切れ後の再配布による照合・再開に委ねます。最終結果の送信に失敗した場合も未送信記録を残し、同じ仕事・epoch・内容で再送します。ログには仕事番号・固定のエラー分類・報告できない工程・待機期限到達を記録し、未検査のエラー本文は出しません。

## 公開と保留

マージの番の更新は直列に行い、接続失敗・5xxなどの一時障害だけを100ミリ秒から最大1秒の待機で再試行します。再試行と実行は最後に確認した期限内に限り、epochと有効な期限が一致する更新応答だけで期限を延長します。更新中でも独立した期限監視が失効時に実行を取り消します。所有権喪失・認証拒否・契約不一致・不正応答では直ちに停止します。

公開・マージ前には停止指示、lease・epoch、マージの番、承認とPRの状態を再確認します。不一致や上限到達時は成果物を残して保留します。

通常公開のマージで HTTP 405 の理由に「Please try again later」が含まれる場合、PRと所有権を再確認しながら上限付きで待って再試行し、上限に達すると review_held に保留します。

状態報告には、計算可能な場合に差分の指紋を付け、既定ブランチの取り込みだけによる承認の引き継ぎに使います。

仕事の作業ツリー・会話ID・工程・結果・使用量は保護された状態領域へ保存します。最終結果と使用量は受付が保存したことを確認してから送信済みにします。再起動時は保存済みの工程と同じ結果を使い、応答を失ったマージはPRの実際の先頭とマージ状態で照合します。

実装回数と重み付き使用量を制限します。独立レビューの回数では保留しません。再開時のレビュー証拠と報告補完の扱いは [実行証拠と検証診断](execution-evidence.md) を参照してください。

継続時に作業ツリーの先頭を照合できない場合の保留理由と再開条件は[継続時の作業ツリー確認](continuation-cause-315.md)を参照してください。

資格情報を含む変更は公開しません。権限保護対象の変更、データ削除SQL、破壊的変更、利用者の判断や不確実性も自動マージせず受付へ保留を報告します。権限の対象集合とコミットはServerの承認記録に照合します。直接PRの権限保護対象・データ削除SQLは、運用代行を許したトークンから届いたPR番号入りの承認、または同じリポジトリ・PR番号・headに一致する保存済みPR作成依頼に付いた8文字以上の承認があるときだけ手動マージの依頼で通し、発言と対象コミットをPRへ記録します。作成依頼の承認も運用代行の印が必要です。

マージ後のブランチは結果の保存後、PRがマージ済みでheadとbaseが同じリポジトリにあり、他の開いたPRがheadまたはbaseに使っていないことを確認してから片付けます。既定ブランチとPRのbaseは削除せず、現在のブランチ先頭がマージ済みheadと一致することも確認します。条件を満たさない場合や確認できない場合はブランチを残します。Issueの作業ツリーの片付けでは、ブランチ確認・削除が一時失敗した場合は作業ツリーも残して後の周期で再試行します。手動マージ依頼では失敗を記録し、保存済みの結果は変更しません。

## 依頼キューとWebhook

PR作成・手動マージ・対象PRのクローズ・main全テストの依頼は、Serverが配った担当リポジトリのものを処理します。対象リポジトリでmain全テストを実行していなければ、手動マージとブランチ指定のPR作成は、仕事の実行中やPCの枠が埋まっている間も処理します。それ以外の依頼はPCに空き枠があり、対象リポジトリの仕事とmain全テストが実行されていない間に処理します。main全テストの開始にはPCの空き枠が2つ以上必要です。

PR作成は依頼IDの目印で重複を照合し、手動マージは依頼時のheadを固定して最新mainに合わせた木の固定テストを確認します。パッチの無いPR作成で、同じブランチから既定ブランチへの開いているPRが既にあるときは、新しく作らずそのPRを結果にします。そのPRの本文にはこの依頼の目印が無いので、この依頼に付けた承認はそのPRの手動マージに効きません（PR番号入りの承認が要ります）。パッチはSHA256とbaseを検査し、公開済みの枝を上書きしません。

手動マージの検証は、試行ごとに取得済みremoteの先頭から独立したdetached作業ツリーを作ります。古いlocalの同名枝や失敗した作業ツリーを再利用せず、既存の枝・未コミットの変更・失敗した試行を保持します。

Webhookは配信設定の待受アドレスでPOST /webhooks/issue-deskを受け、AuthorizationのSHA256を定数時間で照合します。本文は読まず仕事の確認を促します。検証値が未登録ならすべて拒否し、内蔵タイマーの確認を続けます。

生存・負荷・受け取り保留の欄、単位、測定周期と欠測の扱いは [heartbeatの契約](heartbeat.md)、leaseの診断記録は [leaseの診断](lease-diagnostics.md) に記載しています。

## 実行エラーの受付向け分類

実行エラーを報告できる場合、状態の `view.lastExecutionError` に `kind` と UTC の `at` を送ります。`kind` の契約値は次の全11種類です。取得できた失敗時の工程は `stage` に、安全な固定文に完全一致した理由だけを `reason` に追加し、実行エラーログにも同じ値を記録します。 `stage` は失敗時点のメモリ上のjournalの工程です。checkpointは工程を更新してから保存と状態通知を行うため、保存や通知が失敗した場合も移行先の工程を示します（保存失敗時はディスク上のjournalと異なる場合があります）。一覧外のエラー本文は報告・ログに出しません。分類は以下の優先順です。

エラーチェーンを `errors.As` で検索して最初に一致したGitea応答のHTTP statusが100〜599の場合、`giteaHttpStatus` に10進文字列として追加し、実行エラーログに `gitea_http_status=<数字>` を記録します。一致しない場合、最初の一致がnilの場合、または範囲外の場合は省略し、後続のエラーから補いません。この属性は `kind` の分類を変えません。HTTP statusだけでは失敗した操作名・根因・復旧条件を断定できません。

`kind` が `api_rejected` の場合、エラーチェーンで最初に一致した受付API応答のHTTP statusが100〜599なら `intakeHttpStatus` に10進文字列を追加します。Codeは英小文字・数字・`_` の1〜64文字で、固定値と確認済みの `request_failed`、`turn_lost`、`contract_mismatch` に限り `intakeCode` に追加します。ログにも同じ値を `intake_http_status="409"`、`intake_code="request_failed"` のように記録します。一致がない、最初の一致がnil、または各属性が条件外の場合は該当属性を省略し、後続のエラーから補いません。受付クライアントが未知のCodeを `request_failed` に置換する場合があるため、元のCodeを復元できるとは限りません。応答本文やURLなどは記録しません。

| kind | 意味 |
| --- | --- |
| `lease_expired` | 確認済みleaseの期限切れ |
| `lease_lost` | 受付がlease喪失を返した |
| `canceled` | 処理が取り消された |
| `timeout` | 処理の期限切れ |
| `api_rejected` | 受付APIがエラーを返した |
| `provider_report_error` | 実行プロバイダーの報告エラー |
| `provider_usage_limit` | 実行プロバイダーの使用量上限 |
| `transport_failure` | 受付通信の一時的失敗またはネットワーク操作の失敗 |
| `gitea_api_error` | Gitea APIのエラー |
| `filesystem_error` | ファイルパス・リンク・システムコールのエラー（ネットワーク操作を除く） |
| `execution_error` | 上記に該当しない実行エラー |
