# Issue・PRへの投稿

## 共通（outbox）

開始/質問/結果のIssue通知、PRのCOMMENTレビュー、承認時の後続案、再投稿は、POSTの前にoutboxへ試行（attempted）を保存する。応答不明は監視アカウント本人の目印の読取照合だけで回収し、再POSTしない。明確なPOSTの4xx拒否（応答不明になり得る408を除く）だけを確実な不成立とし、通常の通知はpreparedへ戻して再準備できる。GET失敗やtimeoutでは試行を解除しない。仕事に紐づく未送信通知はleaseを失ったら破棄し、長文でも末尾の目印を残す。

訂正報告の未送信記録はlease喪失後も `prepared` に保ち、新しいepochの取得後に送信できる。POSTの応答が不明な `attempted` はコメント取得が恒久エラーでも保持する。旧Workerが `discarded` にした報告も送信有無が不明なため、どちらも再投稿せず、監視アカウントの目印が見つかれば `sent` に進める。

## 承認時の後続案

独立レビューは、`regression`・`acceptance`・`other` の指摘が全件 `minor` なら承認する。再レビューでも重大指摘はmustのまま扱い、既存の保留条件に従って同じIssueの修正へ戻す。直前レビューは同一世代・同一leaseでは上書き前のローカルレビューを優先し、消去後はPreviousReviewを用いる。別PCからの持ち越しでは、レビューに記録した世代、次にlease epochで新旧を選び、戻り先PCに残った古いレビューより新しい配送レビューを採用する。世代情報のない旧形式は受付のworkerExecution.generationを補助に用い、今回世代で生成したローカルレビューを優先する。不正な比較資料で新旧を確定できないときは、古い有効なレビューへの置換を禁止し、承認済みbaselineの再利用も行わない。反復指摘の比較は正規化前に、kindを問わず本文または対応するfindingSpecs.problemの空白正規化後の完全一致（problemは空白正規化後10文字以上の場合のみ使用し、本文との相互比較を含む）と、前回の重大指摘一覧の番号に対する今回のunresolved対応付けで行う。番号は一覧と今回のfindingsでそれぞれ0始まりとし、前回または今回の番号が重複する項目、範囲外の番号、今回のmust以外への対応付けは無視する。resolvedは判定に使わず、欄のない旧レビューは従来どおり照合する。`security`・`data`・`blocking`、未知の種類、minor以外、分類の件数不一致は承認しない。breaking・tooLarge・userJudgments・旧形式のuncertaintiesによる保留は変わらない。

承認時は improvements・findings・resolvableUncertainties を後続案の材料にする。findingSpecsのexpected/testは、Workerが正規化したレビューの improvementSpecs に保存し、findingsを空にした後も保持する。保存済みレビューの保持項目の本文・expected・testは、他の重大指摘や保留条件がある間もレビューJSONのWorker管理欄deferredReviewItemsに保持する。修正後のレビューへ引き継ぎ、消去時にはPreviousReviewへ移し、保存再開・世代持ち越し後も承認時のimprovements/improvementSpecsへ本文の空白正規化キーで重複なく合流する。持ち越し元・ローカル双方の保持項目を合流し、比較元の選択で後続案を失わないようにする。承認済みレビューでpublishから再開する場合もimprovements/improvementSpecsへ合流し、baselineのレビューと照合ハッシュにも反映する。baselineの再利用時にも保持項目と配送履歴を合流する。比較用head・世代・lease epochはreviewedHead・reviewedGeneration・reviewedEpochに保存し、AIの応答値は採用しない。反復保留も選択した直前レビューのheadで判定するため、別PCでの修正後にも同じ重大指摘が残れば保留し、レビュー保存後の同じheadでの再開は反復保留しない。保持項目はrecordOnlyによる配送除外を受けず、無関係なrecordOnly項目は記録を保持して配送から除外する。findingSpecsのexternalCheckOnlyがtrueの項目は本文・expected・testを記録して配送から除外し、falseは本文の語句で除外せず、recordOnlyなど他の配送条件に従う。印のない旧形式は、配備後・配備先・本番・実機・別PC・他のPC・コントローラー・Gitea API・実データ・外部DB・外部データベース・外部サービスのいずれかと、確認・照合・確かめ・検証・接続試験のいずれかを含み、直す・修正・追加・変更・実装・テストを足す・改修・作成を含まない項目を配送から除外する。実装PCという環境の名称は実装作業の指示に数えない。印のない構造化項目では本文に加えexpectedとtestも判定し、詳細が無い場合は本文から期待動作と検査方法を補う。followups/followupSpecs・postMergeChecks・受入条件の移送用 followupIssues は対象外。

投稿は通常のpublish成功の直後、マージ済み照合・権限・削除SQL・手動マージ待ちより前に行う。request_mergeの入口はレビューを受け取らないため、その前の手動マージ待ちまでに投稿を済ませる。差分なしでPRを作らない完了では、元PRが無いことを失敗として残す。

コメントは版3（書式の正本は `internal/execution/proposal_comment.go`）で、version/kind/id/source/title/pr/items/dependsOn/provider/changeScopeの10項目と任意のpriorityを持つ。項目の内部欄interruptReasonに指定された理由は前後の空白を除去し、1〜500 Unicode文字なら同じ理由の項目を通常項目と分け、priorityにlevel=highと理由を設定する。不正な理由は通常項目として扱う。kind=followup、source=元のrepo#Issue、pr=元PRのURL、changeScope=null、dependsOn=[]。providerは実装先がclaudeならclaude、それ以外はcodex。各itemはproblem/expected/testで、各欄はUTF-16で2000文字以内に分割し、1案5件までとする。JSONのHTML文字はエスケープし、投稿前に同じ版3パーサーで検証する。受付側パーサーの変更はWorkerのテストでは検出できないため、版の変更は受付と揃えて行う。

案IDとoutboxの目印は仕事ID・世代・head・バッチ番号から決め、epochやhostを含めない。lease照合には投稿時のepoch/hostを使う。後続案は保持項目の有無を問わず、outboxのattempted保存後・POST前に、各分割項目の位置・内容ハッシュと元の案ID・世代・head・監視アカウント・配送結果の対応をレビューJSONのdeferredReviewDeliveriesへ保存する。本文の複製は配送履歴へ追加しない。保持項目の投稿済み・応答不明の部分は、世代・head・PCが変わっても別の案IDで再POSTしない。通常の後続案は世代・headごとの配送単位を維持する。応答不明は元の監視アカウント本人の目印をGETで照合し、見つかれば同じ案IDの配送結果をsentへ更新する。同じバッチの項目も照合対象として保持する。保持項目のない承認済みレビューへ後から項目を合流する場合も、応答不明の旧バッチのIDと内容は変えず、未試行分には使用済み番号の次のバッチ番号を使う。未試行の分割項目は配送対象に残し、明確なPOSTの4xx拒否（408を除く）は再試行を妨げない。配送履歴と本文・expected・testは、レビュー消去・持ち越し・baseline再利用を経ても保持する。

最終状態はepochを含む送信本文全体で128KiB以内とする。保持項目または配送履歴を含むレビューが上限超過に関わる場合、既存のreview/previousReview欄へ、重複する文字列を辞書参照に置き換えたreviewArchive（version=1、stringsとvalue）を保存する。文字列値だけを辞書番号の文字列へ置換し、オブジェクトのキーと他のJSON型を維持する。別PCでは比較・合流の前にレビュー全体を復元し、journal・baseline・AIへの入力には展開済みレビューを使う。未展開の形式はreviewComparisonBlocked=trueとし、不正な辞書参照・未知の版・8MiBを超える展開は比較不能として扱う。保持必須情報をomittedへ置換しない。縮約と任意報告の省略後も送信上限に収まらない場合は、journalを保持して最終状態の作成エラーを返す。

投稿結果はjournalと最終結果の `followupProposals` へID・世代・head・sent/failed・失敗理由と、配送の確定状態 `deliveryOutcome`（not_attempted/unknown/confirmed/rejected）を残し、受入条件の移送欄とは分ける。後続案の配送失敗でマージや起動時の他の通知の復旧は止めない。journalへの保存失敗や実行中断は通常の実行エラーとして返す。

## 再投稿コマンド（repost_proposal）

このPC宛てで、担当表の `implementers` と配布リポジトリ設定の両方に含まれるリポジトリだけを扱う。担当表の `WorkerAccounts[Host]` が設定され、`gitUser` と異なることを送信のたび（未送信outboxの復旧時を含む）に検査する。Giteaクライアントの本人確認は起動時の `verifyWorkerAccount` が行い、再投稿にも同じ監視用クライアントを使う。元コメントの書き手には `gitUser` を要求し、送信結果の照合では監視アカウント本人の目印だけを信頼する。

コマンド契約にjobId・epochが無いため、lease喪失を理由とした投稿禁止は無い。宛先をこのPCと担当表に限定し、復旧時にも担当・監視アカウントを再検査することで代える。通常の仕事の通知のlease検査は変わらない。

outboxのキーはリポジトリと `<!-- issue-desk-repost:{commentId} -->`。元本文は末尾のgcr目印だけを除いて保持し、最終本文を再解析する。伏字化が必要な本文と、目印を含めUTF-16で55000文字を超える本文は拒否する。コマンドごとの結果は `repost_results.go` が原子的に保存し、outboxの保存後にdone/queuedを返す。queuedは配送完了を意味しない。

POSTの明確な4xx（408を除く）は再投稿をrefusedとして保存し、failed/refusedを返す。refusedは同じ指示・別IDの同じcommentId・復旧のいずれでも再送しない。元コメントの読取は408を含む全4xxを拒否し、通信失敗と5xxはackせず次回へ残す。

コマンドの種類対応表（stop・instruction・repost_proposal）は `pollCommands` とテストが同じ定義を参照する。未知の種類はackしない。受付側で種類を足してもWorkerのテストでは検出できないため、受付と揃えて追加する。

再投稿のエラーは仕事の制御と隔離する。poll中の一時障害は未ackで残し、後続のstop・instructionの処理を続ける。起動時のRecoverと依頼処理のProcessRequestsForも、再投稿1件の障害では止まらない。担当・監視アカウント・本文の安全性の変化、他人の目印、保存済み指示の不一致は、その再投稿を理由付きのrefusedとして保存する。不正・読取不能の結果記録は再生成せず個別に隔離する。ackの409以外の4xxはackRejectedへ保存し、受付に受理された状態とは区別して再送を止める。通信失敗・5xxは次の周回で再試行する。

Giteaのissue_urlはROOT_URLから作られるため、接続先のホスト名との一致は求めない。URLパスの末尾4区切り（owner・repo・固定の区切り・Issue番号）を取り出し、リポジトリは大文字小文字を区別せず、Issue番号は整数として照合する。元コメントの投稿者もアカウント名として大文字小文字を区別せず照合する。

新しい配送結果の応答不明判定はdeliveryOutcomeを使い、診断文の言い換えに依存しません。旧保存データにこの欄がない場合だけ、従来のsent状態と既知の未確認診断から配送履歴を復元します。
