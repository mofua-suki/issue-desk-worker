# フォローアップ起票

独立レビューで見つけた軽微な「実施する」項目について、実装担当が追加の利用者判断や未確認の外部調査をせず着手できる場合に、後続案を作る。重大指摘、保留、利用者判断の既存の判定は変えない。

## 候補の作成

- 独立した挙動ごとに `followupSpecs` の要素を分ける。無関係な問題を一つにまとめない。該当しなければ空配列にする。
- 各候補の問題文を `improvements` または適切な minor の `findings` にも記載し、両方に重複して置かない。`findingSpecs` に同じ問題文の `problem` と候補と同じ `group`・`expected`・`test`、`externalCheckOnly: false` を入れる。findings に対応する findingSpecs は findings と同じ順序にし、findingKinds・findingSeverities も各 finding に対応させる。improvements の詳細は findings に対応する要素の後に置く。重大性の分類は変えない。
- 各要素の `group` は対象を識別できる名前とし、`problem` に対象箇所と再現状況を書く。
- `expected` の最初の独立行を `確認済み根拠: <固定版のパス・節又は行と確認した事実>` とし、続く行に実装後の期待挙動を書く。根拠は実際に読んで確認し、推測で補わない。
- 外部契約は固定版と該当箇所を確認し、実装に必要な仕様を案に写し、合成データで検証できる場合だけ扱う。
- `test` は具体的な確認手段を先に書き、続けて `再現入力: <再現する合成入力>` と `期待結果: <期待結果>` を各1回記す。コロンは半角・全角のどちらでもよく、両ラベルの順序は問わない。各部分に空白や句読点以外の内容が必要。確認手段は対象リポジトリ内で実行できるものとし、資料や指示の文言照合だけを製品の挙動の検証としない。

## 候補にしない項目

根拠が不足する軽微項目は元の findings、improvements または resolvableUncertainties に残し、recordOnly に同じ本文を入れて候補から外す。実APIでの後日確認だけが残る項目は、未確認の内容・理由・確認方法を postMergeChecks に記し、候補にしない。重大指摘や利用者判断が必要な事項は既存の判定と欄を使い、軽微な候補に付け替えない。
